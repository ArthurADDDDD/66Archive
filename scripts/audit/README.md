# 全量条目清点工具（本地、可复用）

这个工具用来做**全库健康清点**：把当前正式条目全部摆出来，让机器先标记结构性矛盾和可疑项，再由人逐条给出最终判断。

> 2026-08-28 已完成过一轮全量结构化扫描与高风险人工复核。那一轮确认了大量游戏 / 标签 / 来源问题，但**不等于逐秒看完所有录像**。这个工具继续保留，用于后续新增数据、批量修正之后的复审。

它**不会自动改 `data/**`**。人工判定只写进本地的 `reviews.json`；真正回写正式档案是独立步骤，判错了可以先在清点工具里改回来，不会直接污染公仓数据。

它和 [`scripts/calibrate/`](../calibrate/README.md) 的结构相近，但任务不同：

- `audit`：**全库**检查“这条记录整体有没有问题”；
- `calibrate`：针对**一批候选**补同一种字段或分类。

---

## 怎么跑

```bash
node scripts/audit/server.mjs
```

然后打开 http://localhost:4174（4173 留给 calibrate）。启动时会按当前 `data/**` 重新读取条目与机器自检结果；中途数据变了，重启即可。

### 从另一台设备连接

```bash
HOST=0.0.0.0 node scripts/audit/server.mjs
```

启动日志会打印局域网地址。

⚠️ 这个工具**没有登录鉴权**。只在可信的家庭 / 办公网内开放局域网访问，不要把端口转发到公网。

多设备一起判断时，每次保存都会先读硬盘上最新的 `reviews.json` 再合并当前条目；工具还会定期生成本地备份，降低误覆盖风险。

## 两种界面

### 快速清点

列表模式把日期、类型、平台、时长、置信度、游戏、标签和机器自检结果放在一行里，适合快速扫过明显正常的条目。

批量“这一页都没问题”只适用于**你确实已经看过这一页**的情况；不要为了追进度把机器没报错等同于人工确认。

### 逐条细看

一次显示一个条目的完整字段、备注、分段和来源链接。判为“有问题”时，应同时指出具体字段（日期 / 标题 / 类型 / 平台 / 时长 / 游戏 / 标签 / 系列 / 链接 / 重复 / 其他）并写清正确方向。

键盘：

| 键 | 作用 |
|---|---|
| `J` / `K` | 下一条 / 上一条 |
| `A` | 上一条 |
| `S` | 判为“没问题”并跳下一条 |
| `D` | 判为“有问题”并跳下一条 |

---

## 机器自检只负责“可疑排序”

机器规则不能替代人类结论。当前大致分两档：

- **high**：结构性矛盾，例如缺日期 / 标题、日期格式异常、未来日期、直播无来源、负时长或超长时长、引用不存在的词表 ID、分段时间超过总时长等；
- **medium**：值得人工看一眼，例如直播缺时长、来源失效或未确认、共享来源、同日近似重复、缺内容标注等。

共享合集、跨日分 P、非游戏聊天场等都可能触发误报。**误报就判没问题，不要为了迁就规则去改档案。**

`propose-tags.mjs` 等启发式建议同样只是候选；标题、分 P、备注能提供线索，但最终是否采纳仍要人工确认。

## 清点之后怎么落到正式档案

`reviews.json` 是本地审校记录，不是正式数据。处理方式按规模选择：

1. **单条且已经核验清楚**：优先用根目录定义的单条安全编辑流程，见 [`../ARCHIVE-EDIT.md`](../ARCHIVE-EDIT.md)。
2. **一批同类问题**：整理成明确的修改计划，人工复核后走项目批准的批量写入链路；公开仓只记录公开层面的流程，不记录生产后台内部表、队列、地址或真实部署命令。
3. 修改进入 `data/**` 后跑 `npm run validate`；涉及游戏词库 / 搜索行为时再跑 `npm run test:vote-search`。

`verdict: skip` 代表证据不足或暂时拿不准，应留给下一轮或交给能查证的人。不要因为“清点要收尾”就把 skip 随手改成 ok。
