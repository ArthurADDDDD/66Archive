# 批量数据校准工具（本地、可复用）

适用于这种任务：**档案里有一批条目需要人工逐条判断，数量大到不适合用单条 `archive:edit` 一个个改，但又不能让机器直接猜完后批量写 `data/**`。**

这个工具把流程拆成：

**机器初判 → 人工逐条确认 → 编译修改计划 → 人工复核 → 走批准的写入链路。**

第一次使用是在 2026-08 给大量缺少游戏归类的条目补标签；后续也可以复用于补分类、游戏、别名或其他“同一类字段的大批量人工校准”。

它**不会自动改 `data/**`**。人工判断写在本地工作文件里；真正进入正式档案前还有单独的计划复核和写入步骤。

与 [`scripts/audit/`](../audit/README.md) 的区别：

- `calibrate`：先圈定**一批候选**，解决同一种字段 / 分类问题；
- `audit`：把**全库**摆出来，检查整条记录是否存在矛盾或漏标。

---

## 整体流程

```text
presort.mjs                 可选：机器给候选做初判建议
      ↓
server.mjs + index.html     人工逐条确认 / 改判
      ↓
note-mapping.json           可选：把自由文本备注映射成结构化 ID / 新词条
      ↓
build-plan.mjs              生成 plan.json，只读、不落盘
      ↓
人工检查 plan.json
      ↓
走项目批准的维护者写入链路
      ↓
npm run validate
```

`suggestions.json`、`decisions.json`、`note-mapping.json`、`plan.json` 都是**当前批次的本地工作产物**，不进版本库。下一批任务应重新生成，不能拿旧批次文件直接套到已经变化的 `data/**` 上。

---

## 怎么跑

```bash
node scripts/calibrate/server.mjs
```

然后打开 http://localhost:4173。启动时会重新读取当前 `data/**` 和词库；中途正式数据发生变化时，重启工具再继续。

### 从另一台设备连接

默认只监听本机。需要在可信局域网里从另一台设备访问时：

```bash
HOST=0.0.0.0 node scripts/calibrate/server.mjs
```

启动日志会打印局域网地址。

⚠️ 这个工具**没有登录鉴权**。只在可信的家庭 / 办公网内开放，不要做公网端口转发。

多设备共同校准时，每次保存都会先读取硬盘上的最新决策文件再合并当前条目，并定期保存本地快照，避免一台设备拿旧内存整份覆盖另一台设备的结果。

---

## 人工判断通常分两步

### 第一步：粗分类

只回答“这条是否属于本批次要处理的对象”。例如第一次任务问的是“这场是不是在玩游戏”。

这一阶段不要被具体游戏名、别名等细节拖慢；拿不准就保留为待确认。

### 第二步：补细节

只处理第一步已确认属于本批次的条目，补具体 ID、别名或新词条。搜索应以完整受控词库为准；词库没有时先记录为“需要新建”，不要临时造一个相似 ID 硬塞进去。

如果下一批任务不需要“粗分类 + 补细节”两层，可以调整该批次的界面逻辑，但仍要保留**机器建议与人工结论分离**的原则。

---

## 机器初判只是建议

`presort.mjs` 的规则通常是**批次专属启发式**，不是通用真相。标题、分 P、备注、相邻日期都只能提供线索，尤其要防止：

- 把“看 / 聊 / 联动某游戏”误判成真的在玩；
- 因为续作标题自动补前作；
- 把相邻分 P 的游戏错挂到当前条目；
- 因为标题宽泛就强行补“聊天”；
- 把上传日期当成直播日期。

人工已经核实过的判断应高于机器规则；改启发式时不要覆盖已有人工决策。

---

## 编译计划

当人工判断完成后，可通过 `note-mapping.json` 把自由文本说明映射为明确结构，再运行：

```bash
node scripts/calibrate/build-plan.mjs
```

`plan.json` 应至少让人能检查：

- 新增哪些游戏 / 标签 / 别名；
- 哪些 entry 要改、改什么字段；
- 哪些仍未解决；
- 是否出现词表不存在、重复 ID、备注与选择矛盾等问题。

**`build-plan.mjs` 只负责生成计划，不应直接写正式档案。**

---

## 怎么应用回 `data/**`

1. 人工完整检查 `plan.json`，确认这一批的证据和映射没有明显错误。
2. 按项目批准的维护者写入方式提交这批修改。公开仓只描述“需要人工确认后才能落盘”这一契约，**不要在这里记录生产后台的内部表名、队列名、真实地址、服务器目录或部署命令**。
3. 如果最终只剩一两条独立修正，优先拆出来用 [`../ARCHIVE-EDIT.md`](../ARCHIVE-EDIT.md) 的单条流程，不要为了两条数据继续跑整批链路。
4. 落盘后运行：

```bash
npm run validate
```

涉及游戏词库或搜索行为时再运行：

```bash
npm run test:vote-search
```

任何无法由现有证据确认的项都应留在待处理列表里，而不是为了让批次“100% 完成”强行写入。
