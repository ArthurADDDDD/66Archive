# 批量数据校准工具（本地、可复用）

一个通用套路：**档案里有一批条目需要人工逐条判断，量大到不能靠单条 `archive:edit`
过，又不能瞎猜批量写 `data/**`。** 这个工具把「机器初判 → 人摆出来点是/否 →
编译成计划 → 走暂存/落盘」这条流水线跑起来，第一次是为了给 1018 条没有游戏
标签的条目补标签而做的（2026-08），但设计上跟那一批数据没有绑定——下次
不管是补标签、改分类还是任何「量大、需要人工逐条确认」的批次任务，都可以照这个
流程重新走一遍。

**它不会碰 `data/**`。** 人工判断只写进本地的 `decisions.json`；真正回写档案是
最后一步单独做的，判错了在这个工具里随时改回来，不会污染档案。

---

## 整体流程（复用时照这个顺序走）

```
presort.mjs          机器给每条一个初判建议，写进 suggestions.json（可选）
      ↓
server.mjs + index.html   人工在网页上逐条确认/改判，存进 decisions.json
      ↓
（人工编写）note-mapping.json   把决策里的自由文本备注映射成具体的游戏 id / 新游戏 / 标签规则
      ↓
build-plan.mjs        编译成 plan.json：新游戏、新标签、条目改动、还没搞定的、有问题的
      ↓
（读 plan.json 人工核对无误后）通过后台的暂存机制（archive_staged_*）批量提交
      ↓
后台控制台确认落盘 → 推送到公仓 main → 部署
```

`suggestions.json`、`decisions.json`、`note-mapping.json`、`plan.json` 这些都是
**某一批次的工作产物**，不进版本库（见 `.gitignore`）——下次复用时会重新产出全新的一份，
不能延用上一批留下的文件，否则会跟当时 `data/**` 的真实状态对不上。

## 怎么跑

```bash
node scripts/calibrate/server.mjs
```

然后打开 http://localhost:4173。启动时会打印这一次的条目数、词库数——
数据是现读 `data/**`，永远反映当前真实状态。中途 `data/**` 变了，重启一下即可。

### 从另一台设备（比如 PC）连进来

默认只监听这台机器自己（`127.0.0.1`），局域网内的其他设备连不进来。
要开放局域网访问：

```bash
HOST=0.0.0.0 node scripts/calibrate/server.mjs
```

启动日志会打印出局域网可用的地址，例如 `http://192.168.x.x:4173`，
在同一个路由器下的另一台设备浏览器里打开就行。

⚠️ 这个工具**没有任何登录鉴权**——局域网内任何设备都能连上来改。
只在你信任的家庭/办公网络里这样开，不要把这个端口转发到公网。

### 两台设备一起改，安全吗

安全。每次保存都是先读硬盘上最新的 `decisions.json` 再合并这一条，
不是拿内存里的旧快照整份覆盖，所以两台设备各自存不同的条目不会互相吞掉。
左栏的进度条每 12 秒自动跟服务端同步一次，切回这个标签页时也会立刻同步一次。

每存 20 次，`decisions-backups/` 里会多一份带时间戳的快照，
误操作把判断清没了可以从这里翻回来。

## 界面分两步，别混着做

**第一步 · 粗分类** —— 只回答一个问题：这条到底属不属于要处理的这一类
（第一次是「是不是在玩游戏」）。界面这时会把细节选择框藏起来，只剩几个按钮，
就是为了让你不用分心去想细节。`S` = 是，`N` = 不是，`K` = 拿不准。

**第二步 · 补细节** —— 只列出第一步里被确认「是」的条目，逐条填具体信息
（第一次是填具体是哪款游戏）。搜索框搜的是完整词库（名字、别名、id 都能搜），
词库里没有的**直接回车登记成新条目**，落盘时会一并加进对应的词表文件。

这个两步结构是为「粗分类 + 细节判断」这种任务设计的，如果下次的任务不需要
两步（比如只是单纯的是非判断），改 `index.html` 里的 `STEP` 逻辑，把第二步跳过即可。

## 机器初判只是建议，请随便否

每条上面会显示机器给的初判（如果跑过 `presort.mjs`）。**它会错**，
标了 ⚑ 的是机器自己觉得可能判错的矛盾项，建议优先看这批
（左栏筛选「只看『可能判错』」）。

`presort.mjs` 里的规则是**为第一次那批数据写的**，复用时大概率要重写这些规则——
把它当成「这次批次专属的启发式」而不是通用逻辑。已经人工看过的条目可以
写进一份 `judgments.json`（`{ entryId: verdict }`），优先级高于机器规则，不会被覆盖。

## 键盘

| 键 | 作用 |
|---|---|
| `J` / `K` | 上一条 / 下一条 |
| `S` | 第一步：确认属于这一类；第二步：保存 |
| `N` | 不属于这一类 |
| `T` | 第二步：标题已经说明白了，不必登记具体条目 |
| `/` | 跳到搜索框 |
| `↑` `↓` `Enter` | 在搜索结果里选 |
| `Esc` | 清空搜索 |

## 改完之后：怎么应用回 `data/**`

1. 写一份 `note-mapping.json`，把 `decisions.json` 里的自由文本备注映射成机器能用的结构：
   - `newGames`：`{ id: { name, aliases } }`，新登记的条目
   - `entries`：`{ entryId: [id, ...] }`，备注里写了具体名字但没在页面选择框里选的
   - `reclassify`：`{ entryId: kind }`，备注跟第一步判断矛盾时以备注为准
   - `aliasAdditions`：`{ id: [alias, ...] }`，给词库里已有条目补别名
2. 跑 `node scripts/calibrate/build-plan.mjs`，产出 `plan.json` + 终端摘要
   （新增数量、要改的条目数、还没解决的、检测到的问题）。**这一步只读不写。**
   人读一遍 `plan.json`，确认没问题再往下走。
3. 应用计划本身走项目现有的暂存/落盘机制（见仓库根 `AGENTS.md`「改动怎么才能上线」），
   不要绕开它直接改 `data/**`——暂存机制自带 evidence 记录、并发保护和后台确认这一关。
   如果 `plan.json` 里有暂存 schema 承载不了的字段（比如这一次的 `type` 和游戏别名），
   把这部分拆出来单独走一次隔离 worktree + 逐字段自校验 + 直接 push 的小改动，
   范围要小到能被完整核对，不要跟主批次混在一起。
4. 跑 `npm run validate`（以及涉及游戏词库改动时的 `npm run test:vote-search`）确认没写坏。

## 重新生成机器初判

改了 `presort.mjs` 的规则之后：

```bash
node scripts/calibrate/presort.mjs
```

`judgments.json`（人工逐条看过的）优先级高于机器规则，不会被覆盖。
**这一步只重算建议，不会动 `decisions.json` 里已经做的判断。**
