## 一、数据模型

数据以 YAML 存在仓库中，构建时用 zod 校验并编译成静态 JSON + 搜索索引。

### 1. Platform（平台，枚举常量）
`youku` / `bilibili` / `youtube` / `douyu` / `douyin`

每个平台带：中文名、品牌色、图标、URL 匹配规则（用于从粘贴的链接自动识别平台并抽 ID）。

### 2. Account（账号）
```yaml
id: bili-official
platform: bilibili
name: 女流66
url: https://space.bilibili.com/xxxxx
role: official        # official | mirror | fan-archive
active_from: 20xx-xx  # 待考证
note: ""
```
`fan-archive` 用来标记热心网友的录播搬运号——这类账号在直播期是主要资源来源，必须建模。

### 3. Game（游戏）
```yaml
id: dark-souls-3
name: 黑暗之魂3
aliases: [魂3, Dark Souls III]
cover: /games/ds3.jpg
first_played: 20xx-xx-xx   # 由数据自动推导，不手写
```
游戏是**一等公民**，因为「每一次直播播了什么游戏」是本站的核心诉求。

### 4. Entry（条目 —— 统一的时间轴单元）

两种子类型共用一套外壳，这样时间轴可以混排：

```yaml
id: 2024-03-15-live-01
type: live            # live | video
date: 2024-03-15
time: "19:30"         # 可选
title: "……"
platform: bilibili    # 首播平台
duration_min: 245     # 可选
series: xxx-playthrough   # 可选，归属系列
games: [dark-souls-3]     # 该场次涉及的游戏
tags: [杂谈, 联动]
cover: https://...    # 原平台封面 URL，前端过代理
confidence: high      # high | medium | low
sources:              # ★ 多源：官方回放 + 各路录播
  - url: https://www.bilibili.com/video/BVxxxx
    account: fan-archive-abc
    kind: replay      # original | replay | clip | reupload
    parts: 3
    status: alive     # alive | dead | unchecked
segments:             # ★ 分段：这场几点开始打什么
  - at: "00:12:30"
    game: dark-souls-3
    label: "开荒第一天"
  - at: "03:40:00"
    game: null
    label: "杂谈 / 读评论"
contributed_by: github-username
```

关键设计点：

- **一场直播 = 一个 Entry，可以挂 N 个 source。** 这样「B 站官方回放 + 三个网友录播」是同一场，不会在时间轴上重复出现四次。
- **segments 承载「播了什么游戏」的时间精度**，也是详情页迷你进度条的数据来源。允许为空（先录粗粒度的 `games`，后补时间点）。
- **video 类型**只是 segments 为空、通常单 source 的 Entry。

### 5. Series（系列）
如某个游戏的完整实况，跨多场。用于把时间轴上散落的条目串成一条线。

### 6. Era（时期）
`video-era` / `live-era`，带起止时间与一段导语，驱动时间轴的视觉与叙事分段。

## 二、页面与功能

### P1 · 主时间线（首页，核心页面）

**布局（桌面 ≥1280px）：三栏**

```
┌──────────┬───────────────────────────────┬──────────┐
│ 筛选侧栏  │        时间线主区              │ 年份刻度尺 │
│ 平台      │  ○─ 2024-03-15  直播 · 黑魂3   │   2026 ▁ │
│ 类型      │  │   [卡片，hover 出预览]      │   2025 ▃ │
│ 游戏      │  ○─ 2024-03-14  视频 · ……      │   2024 ▇ │
│ 系列      │  │                             │   ...    │
│ 年份区间  │                                │   2010 ▁ │
└──────────┴───────────────────────────────┴──────────┘
```

- **垂直无限滚动**，按时间倒序（可切正序）。日期用 sticky 分组头（年 → 月）。
- **右侧刻度尺**：每年一格，格子高度/亮度反映当年条目数（密度热力）。可拖拽快速跳转，滚动时高亮同步。
- **时期分隔带**：滚过「视频期 → 直播期」的分界时，插入一条整幅的过渡段落，配色随之切换（视频期偏暖的胶片/CRT 质感，直播期偏冷的霓虹）。这是全站叙事的转折点，值得做重。
- **卡片信息层级**：日期 → 标题 → 平台徽标 + 时长 + 游戏标签 + 源数量徽章（`3 源`）。失效条目降饱和度并标「链接已失效」。

**Hover 预览（明确要求项）**

- 桌面：指针停留 ~150ms 后，在卡片侧边弹出浮层——大图封面、完整标题、平台、时长、游戏标签、分段小时间条、可点的多个源链接。浮层跟随边界自动翻转，不越出视口。
- 封面**懒加载 + 低清占位**（LQIP 模糊过渡），走图片代理绕开防盗链。
- 触摸设备没有 hover：卡片点击 = 就地展开为同样内容的行内面板（不跳页），再点标题才跳详情页。这是响应式的关键分歧点，不要用 hover 的移动端模拟（长按）来凑合。

**筛选与搜索**
- 平台（多选）、类型（直播/视频）、游戏（带搜索的多选）、系列、年份区间双滑块、「只看有存活源的」开关。
- 全局搜索框（`/` 唤起）：标题 + 游戏别名 + 标签，本地索引即时匹配，结果直接筛选时间线而不是跳到搜索结果页。
- **所有筛选状态写进 URL query**，链接可分享、可回退。

### P2 · 条目详情页 `/e/[id]`
- 头部：日期、标题、平台、时长、系列上下篇导航（← 上一场 / 下一场 →）。
- **分段时间轴**：一条横向进度条，按 segments 切块并标注游戏与节点名，点击某段直接跳到对应源的带时间戳链接（B 站 `?t=`、YouTube `&t=`）。
- **源列表**：每个源显示 UP 主、类型（官方回放/录播/切片）、分 P 数、存活状态、录入者。
- 相关：同游戏的其他场次、同系列前后条目。

### P3 · 游戏库 `/games` 与游戏页 `/games/[id]`
- 库页：游戏封面网格，按首次游玩时间/场次数/总时长排序，带搜索。
- 游戏页：这个游戏的完整时间跨度甘特条 + 所有相关场次列表 + 总时长/场次数统计。「他打这个游戏打了多久」在这里一眼可得。

### P4 · 统计 `/stats`
- 年度产出柱状（视频 vs 直播分层）
- 平台迁移图（按年份的平台占比堆叠面积，能直观看出优酷→B站→斗鱼→抖音的迁移）
- 游戏时长 Top 20
- **数据覆盖率看板**：按月网格，颜色表示该月已录入条目数，空白格 = 待补录（同时是给志愿者看的「缺口地图」）

### P5 · 贡献 `/contribute`
- 说明数据格式与原则。
- 表单：粘贴链接 → 自动识别平台并抓取可公开获取的标题/日期/时长 → 补充游戏与备注 → 生成一段 YAML 并一键跳转到预填好的 GitHub Issue（阶段一不做后端，零运维）。

### P6 · 彩蛋级小功能
- **「那年今日」**：首页顶部一行，展示历史上的今天他在播什么。
- **随机考古**：随机跳一个条目。
- 键盘操作：`j/k` 上下条目、`/` 搜索、`f` 收起筛选栏。

## 三、响应式规则

| 断点 | 布局 |
|---|---|
| ≥1280px | 三栏（筛选 / 时间线 / 刻度尺），hover 预览浮层 |
| 768–1279px | 两栏（时间线 + 刻度尺），筛选收进顶部抽屉 |
| <768px | 单栏卡片流；筛选为底部 sheet；刻度尺变成顶部 sticky 的年份快速跳转条；hover → 点击行内展开 |

其他：`prefers-reduced-motion` 时关闭视差与过渡动画；深色为默认主题，浅色可切换；封面图全部走 `content-visibility` + 懒加载，保证几千条目下滚动不掉帧（列表用虚拟滚动）。

## 四、技术方案

- **Next.js 15（App Router）+ TypeScript + 静态导出**。全站预渲染，无服务端，部署到 Cloudflare Pages / Vercel，成本近零。
- **Tailwind CSS** + 自建少量组件；动画用 Framer Motion（克制使用）。
- **数据管线**：`/data/**.yaml` → zod 校验（CI 里跑，格式错的 PR 直接红）→ 生成 `entries.json`、`games.json`、搜索索引 → 构建期注入。
- **搜索**：数据量在万条以内，用 MiniSearch 在客户端建索引即可，不需要服务端。
- **图片代理**：一个 Cloudflare Worker 做封面转发 + 缓存 + 尺寸压缩，绕开防盗链且不占源站带宽。
- **链接存活检查**：GitHub Actions 定时跑脚本，把 `status` 写回 YAML 并自动开 PR。
- **阶段三的自动抓取**同样跑在 Actions 里，产物是 PR 而不是直接写库——保持「所有数据变更可审计」。

## 六、建议的实施顺序

1. `src/lib/schema.ts` 定义 zod Schema + 手写 20~30 条真实种子数据（跨两个时期），先验证模型是否够用
2. 时间线骨架 + 卡片 + 日期分组
3. hover 预览 + 图片代理
4. 筛选/搜索 + URL 同步
5. 详情页 + 分段时间轴
6. 游戏库、统计、贡献页
7. 视觉打磨（时期配色过渡、动效、空状态）
