## 你的角色边界

角色是任务的功能位，不是绑死给某个模型品牌的身份证。**Claude 额度不够时，你可以顶上"架构/前端"（角色 A）**，不是只能干工具/自动化那一份——这份交接默认建议你先接角色 C，但如果人类直接指派你做前端/组件/页面，同样可以，照角色 A 的边界来就行。

**唯一的硬规矩：一次会话只扮演一个角色，开工前明确声明是哪一个**，不要一边写前端一边顺手改数据、或者一边写自动化脚本一边顺手改 Schema。

| 角色 | 可以写 | 不能碰 |
|---|---|---|
| C · 工具与自动化（默认建议） | `scripts/**`、`.github/**`、测试 | UI 组件、`src/lib/schema.ts`、`data/entries/**` 的内容本身 |
| A · 架构与前端（Claude 缺席时可顶上） | `src/**`、`docs/**`、`src/lib/schema.ts` | 批量写 `data/**` 业务数据 |

**Schema 的强约束不变**：不管这次是谁扮演角色 A，同一时刻只能有一份权威修改；改了 Schema 必须同步更新 `docs/02-功能设计.md` 的数据模型章节和本文档。发现字段不够用但你这次不是角色 A，就写 `docs/rfc/NNN-xxx.md` 提 RFC，不要私自加字段。数据内容（哪场直播、播了什么游戏）永远是角色 B（数据采集）的工作，不管你这次扮演 A 还是 C 都不属于你——你可以验证/检查/自动化数据管线，不产出数据内容本身。

提交前必须跑：
```bash
npm run validate
```
一个 PR 只做一件事，数据 PR 不夹带代码改动，反之亦然。

### 自动化侧 —— 这是你的主战场，目前完全空白
`scripts/` 目录现在只有两个文件：`validate.ts`（校验闸门）、`gen-demo.ts`（演示数据生成）。`.github/` 目录不存在。以下是 `docs/02-功能设计.md` 里写过、但从未实现的自动化，按价值排序：

1. **CI：`.github/workflows/validate.yml`**
   跑 `npm run validate`，PR 触碰 `data/**` 或 `src/**` 时触发。`docs/03` 里写了"PR 必须通过 CI 才能合并"，但这条闸门现在实际上不存在——任何人现在提交坏数据都不会被自动拦截。这是优先级最高的一项。

2. **链接存活检查：`scripts/check-links.ts`**
   遍历所有 `sources[].url`，探活后把 `status: alive/dead/unchecked` 写回对应 YAML 文件。设计上应该能被 GitHub Actions 定时跑、自动开 PR（不要直接 push 到 main）。2748 条数据现在全是 `unchecked`，这个脚本一旦跑起来价值很大——前端已经有失效链接的降饱和度/划线展示逻辑在等着这份数据。

3. **封面图代理**：`src/lib/platforms.ts` 里的 `proxyImage()` 已经预留了 `NEXT_PUBLIC_IMG_PROXY` 环境变量的接口，等一个真正的图片代理服务（Cloudflare Worker，绕开 B 站防盗链、控制尺寸）。现在没有这个 env var 时代码会直接用原图，够用但会被防盗链挡。

4. **（不急）搜索索引化**：现在时间轴的筛选/搜索是在客户端对全量 2748 条内联过滤，实测依然是即时响应，2748 条这个量级不需要优化。`02-功能设计.md` 提过 MiniSearch 方案，等数据量明显上一个量级（比如视频期全部收完、破万条）再考虑，现在做是过早优化。
