# 采集任务 #006 · 标题清洗（机械抽取遗留问题）

> 接入真实数据到前端时发现的批量问题，性质上和 #003（日期提取 bug）是同一类：
> 抽取脚本的规律性缺陷，不是个别脏数据，适合批量修复而不是逐条人工改。

## 范围
`data/entries/**` 全量，两类问题：

### 问题一：HTML 实体未解码（约 90 条标题）
标题里直接留着 `&amp;` `&quot;` `&#39;` 等字面量，应解码为 `&` `"` `'`。

```yaml
# 现状
title: "下鸭神社&amp;六道珍皇寺之旅"
title: "Don t cut your hand &amp; 欧洲卡车模拟2"

# 应为
title: "下鸭神社&六道珍皇寺之旅"
title: "Don t cut your hand & 欧洲卡车模拟2"
```

### 问题二：标题开头的「【」被误删（约 107 条标题）
源标题格式通常是『【女流66】【日期】[游戏/内容]』，抽取时把开头的「【女流66」连同前导「【」一起吃掉了，
只留下孤立的「】」，读起来像断句错误：

```yaml
# 现状（孤立的】很显眼）
title: "女流66】【2025-11-14】[没错 就是使命召唤]"
title: "女流66】4月份之前播鸣潮2.7！……"

# 应为（补回前导【，或者干脆把固定的"女流66】【日期】"前缀整体去掉，只留内容部分）
title: "【女流66】【2025-11-14】[没错 就是使命召唤]"
# 或者更干净：
title: "没错 就是使命召唤"
```
两种修法都可以，但**全库要统一成一种**，不要一部分留前缀一部分不留。建议采用后者
（只保留内容部分），因为『女流66』『日期』已经是页面上独立展示的字段，标题里重复反而是噪音。

## 硬性规则
1. 这是格式清洗，不是内容核实——不要在这轮顺带改动日期、平台、游戏标签等其他字段
2. 改完标题后跑 `npm run validate` 确认结构仍然通过
3. 交付时给出修复前后的 diff 统计（改了几条、按问题类型分别计数），方便复核
4. 如果清洗过程中发现标题原本就包含真实的「】」（比如内容本身引用了另一层标记），
   保留原样，不要误伤，交付说明里单独列出这类特例

## 交付时必须说明
- 两类问题各修复了多少条，是否有遗漏未处理的（比如标题里还有其他未列出的转义字符）
- 是否发现了新的第三类抽取痕迹（比如多余空格、全角/半角混用），如果有，一并列出但不必这轮处理
