## 4. 与单 basis 口径兼容的方案（未改 Schema）

当前 `GameTimeline` 的关键约束是：一场直播只有一条 `basis`，所有时长只按这条来源计算。由此有三类情况：

### A. 单一来源覆盖整场，且游戏从分 P 开头开始

**做法：直接切换 basis**，如 2017-12-13。这是最干净的方案，不需要 Schema 改动，也不跨来源相加。
适用：2017-12-13（已实施）。

### B. 整场分散在多个视频，没有单一来源覆盖全部

例如 2016-08-17、2017-01-18、2017-04-04、2023-09-17、2023-11-09、2015-01-27、2016-01-04。
**建议：保留主 basis 计时，新增“补充跳转”映射，只用于导航，不参与时长统计。**

一种最小 Schema 提案（待评审，不直接实施）：

```yaml
# 仍保留唯一 basis 和 spans；另加可选的补充跳转
alternate_jumps:
  - game: super-bomberman-r
    source: https://www.acfun.cn/v/ac3601511
    page: 1
    at: 00:00:00
    precision: part
    evidence: part_title
```

UI 在游戏页/条目页显示“其他来源”入口；`recordedSec`、`associatedSec`、`verifiedSec` 仍只由主 basis 计算。
这样不会出现“不同来源时长相加”，也不需要把两套时间轴混在一条 spans 里。

### C. A 站来源中游戏起点在分 P 中间

例如 2022-11-02（The Past Within 约 4:46:20）、2023-09-17（猛兽派对约 0:04:10）、2023-11-09（魔法工艺约 0:29:50）。
A 站 URL 没有可用的秒级参数，只能跳分 P 开头。即使加了 `alternate_jumps`，也只能做到“跳到 P2/P1 开头”，不是精确起点。

可选方案：

1. **只做分 P 级跳转**，并在 UI 明确写“A 站只能到分 P 开头”，不宣称精确。
2. 寻找同一内容的 B 站镜像；B 站支持 `?p=&t=`，可做秒级跳转。
3. 若必须对 A 站做秒级跳转，需要后台/前端增加“打开后自动 seek”的交互或浏览器扩展，不属于当前数据 Schema 范围。

本轮不实施 B/C 的 Schema 或前端改动，只记录证据与方案，等待评审。
