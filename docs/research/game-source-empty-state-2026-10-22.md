# 游戏录像留空与切片占位调查（2026-10-22）

范围：按当前公开数据集和实际前台投影逻辑复算全部直播条目，再检查游戏时间轴处置清单与条目备注。没有新下载或观看媒体，没有修改正式档案或前台代码。以下“可用”均指现有 `status: alive`，不是本轮重新验证链接存活。

## 规则与实际行为

AGENTS.md 要求未核实的数据留空或标 low，不允许合理推测填充。Schema 还明确区分：没有任何公开录像用 `no_public_replay`；有录像但缺内容用 `missing_footage`；`sources.kind: clip` 是切片，不是整场完整性证明。`replay` 同样只表示录播类别，不能证明完整。

因此，已知发生过的直播可以保留日期记录，但没有找到的对应游戏录像应明确缺失，不应把其他游戏的切片当成该游戏观看入口。切片可以保存为残存资料，必须让读者看得出其范围；推断的游戏标签也不能无区别地显示为已确认内容。当前规则没有要求删除所有缺录像的历史场次，但要求不伪造缺失内容。

当前有五处逻辑共同造成截图现象：

1. `src/lib/narrative.ts:getGameProfile` 只按 `entry.games` 或有限策展标题规则选场次，不检查来源是否覆盖当前游戏。
2. `src/lib/data.ts:toTimelineEntries` 把第一个 alive 来源当成 `primaryUrl`，没有按切片、覆盖范围或当前游戏筛选；没有 alive 时仍回退到第一条来源，包括 dead。
3. 游戏页给 `GameSessions` 传入整条场次，不传当前游戏作为选源条件；共享详情卡也没有“这款游戏录像缺失”的状态。
4. `EntryDetail.tsx` 的来源按钮使用 `平台名称 ?? 来源类型`，平台已知时显示 AcFun/B站，切片类型被隐藏；`sourceCaption` 只展示 label 或不同的条目标题，不展示来源 note。截图条目的推断与不完整说明都在 note 中，因此这张卡看不到。
5. `EntryClue` 只在没有 alive 来源或填写了 `missingFootage` 时出现。只有 alive 切片、未填缺段字段的条目不会自动提示“录像不全”；`chapterCoverage: partial` 也不触发这条提示。

独立条目页 `EntryWatch` 会显示来源类型，信息比游戏页共享展开卡更完整，但同样按第一个 alive 来源选源，也不会自动将 clip-only 判断成“完整录像缺失”。这是页面之间显示口径不一致。

## 建议处理口径（本轮未实施）

- 保留有证据的直播日期记录；对应游戏无可确认录像时，游戏观看位置明确为空/未找到，停止以同场其他游戏替代。
- 切片独立标为残存片段，保留链接，但不作为完整录播的默认替代品。replay 也必须区分覆盖范围，不能只修 clip 判断。
- 已有互补来源时按当前游戏提供经过证据确认的入口；尚未确认的来源不能伪装成已补齐。
- 统一游戏展开卡与条目页的来源类型、缺段和失效提示。备注中明确的缺段应进入可展示状态；不能只留在读者看不到的 note 中。
- 推断游戏标签单独待核，不把 missing_footage 或前台提示当成证据确认，更不能直接批量删除有独立同期记录的游戏标签。

尚未确认：没有时间轴的绝大多数场次的逐游戏来源覆盖；文本中“剪辑”与“完整页并存”的逐 P 实际结构；历史 alive 的当前存活状态。正式数据未变，confidence: low 变更不适用。本报告是模型自检，没有人工完整观看或独立人工审校。
