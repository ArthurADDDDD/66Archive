# 游戏时间轴与游戏环节时长

精准跳转（从游戏页跳到长录像里这款游戏开始的位置）和游戏时长统计，共用同一份数据：`data/game-timelines.yaml`。
**本页是这两件事唯一的口径定义。** 写时间轴、审阅时间轴、改任何显示游戏时长的界面之前先读本页，不要另行换算。

实现：契约在 `src/lib/schema.ts`（`GameTimeline`），计算在 `src/lib/game-time.ts`，与条目的交叉校验在 `src/lib/game-timeline-check.ts`（`npm run validate` 调用），测试是 `npm run test:game-time`。

## 1. 统计对象：游戏环节时长

统计的是**游戏环节**的时长，不是逐秒扣除加载、读档和停顿后的纯操作时间。

- **游戏环节**：从这款游戏开始进行（游戏画面、启动器或加载画面第一次出现，或主播明确开始玩）起，到下一个环节开始或录像结束为止。环节内的加载、读档、菜单、边玩边聊、短暂离开、操作停顿全部计入。
- **同款游戏的中途休息（2026-10-18 维护者修订）**：`A → break → A` 作为一个完整游戏环节，休息计入 A 的关联录像时长，不按休息长度拆碎。连续多个 break 也按此处理。只在两侧是同一具体游戏 ID 时合并；`A → B → A`、夹有 unknown、仅属于同系列但作品不同都不合并。旧审核记录原样保存，合并在展示和统计中派生，不改写 `human_watch` / `scanned`。休息没有原有人工内部检查时，其秒数只进关联录像，不自动升为已核实；合并也不抹掉两侧原已核实的秒数。
- **其余独立环节**（`kind: break`，不计入任何游戏）：连续 **5 分钟及以上**（`INDEPENDENT_SEGMENT_MIN_SEC = 300`），且这段时间的主要活动不是游戏：开播 / 下播聊天，专门的聊天、读弹幕或答谢环节，吃饭、休息、挂机画面，看视频，抽奖，其他节目（唱歌、连麦、户外等）。判断看「主要活动」：游戏画面虽然挂着，但主播已经转去聊别的话题 5 分钟以上，也算独立聊天。
- 短于 5 分钟的上述情况并入所在的游戏环节；两款游戏之间的切换间隙短于 5 分钟的，并入前一款游戏。
- 同一款游戏被其它游戏或 unknown 打断后再回来，仍是不同环节，分别跳转；夹在同款游戏之间的 break 按上述规则合并。开播前、下播后以及不同游戏之间的独立环节仍排除。
- **已核实**：环节两端都经人工在录像里定位（误差 ≤1 分钟，`evidence: human_watch`），**并且**人工检查过环节内部，确认没有遗漏的独立环节（`scanned: true`）。只定位了两端、没有检查内部的，不算已核实。模型或脚本读缩略图、弹幕得出的位置（`thumbnails` / `danmaku`）精度可以到分钟，但只进「关联录像」，不能冒充人工审核。

## 2. 时间轴

一场直播一条时间轴，只认一个**计时基准来源**（`basis`）。环节首尾相接，覆盖整份基准录像；位置写成「第几个分 P + 分 P 内时间」，因此不受来源续号、缺 P、跨投稿的影响。

```yaml
- entry: 2020-08-10-live-01              # 同场合并组的代表条目
  basis: https://www.bilibili.com/video/BV1iK4y1v7AT
  coverage: complete                     # complete | partial | unknown
  parts:                                 # 基准来源的分 P 快照，按播放顺序
    - { page: 1, id: 222891209, duration_sec: 2655 }   # B 站 id = cid；A 站 = video id
    - { page: 2, id: 222904473, duration_sec: 2655 }
    - { page: 3, id: 222914143, duration_sec: 3414 }
  spans:                                 # 每个环节从这里开始，到下一个环节开始或录像结束
    - { page: 1, at: '00:00:00', game: paper-mario, precision: part, evidence: part_title }
    - { page: 3, at: '00:00:00', game: fall-guys, precision: part, evidence: recording_break }
    # 人工定位：{ page: 3, at: '00:07:12', game: ..., precision: approx, evidence: human_watch, scanned: true }
    # 独立环节：{ ..., kind: break }    还没核对：{ ..., kind: unknown }
  reviewed: "2026-10-17"                 # 人工确认日期，要加引号；没有它不能入库
```

| 字段 | 规则 |
|---|---|
| `page` | B 站页号；A 站为 videoList 数组序（1 起，跳转 `_N` 用它，不是标题里的 P 号） |
| `precision` | 环节**起点**的精度：`part` 只知道在这个分 P 开头附近（`at` 必须是 `00:00:00`）；`approx` 误差 ≤1 分钟；`exact` ≤10 秒。录像开头和结尾本身算精确 |
| `evidence` | `part_title` 录像组分 P 标题、`recording_break` 分 P 时长显示录像在此重新开始、`thumbnails` 模型或脚本读平台缩略图帧、`danmaku` 弹幕、`human_watch` 人工在录像里核对、`other`。前两种只能配 `precision: part`。`human_watch` 只能由人工审阅写入 |
| `coverage` | 基准录像是否覆盖整场。分 P 不是从 P1 起连续的，不能标 `complete`；`complete` 时条目 `games` 里的每款游戏都必须有环节 |

交叉校验还要求：`entry` 是同场合并组的代表条目，同一场只能有一条；`basis` 是这一场某条来源的 url，平台目前限 B 站、A 站；环节里的游戏都在条目的 `games` 里。时间轴只能经人工确认后写入，生成工具不改 `segments`，也不改条目文件。旧的 `segments` 保留原样，只用于进度条。

## 3. 三档时长

每场 × 每款游戏只会落进其中一档：

| 档位 | 来源 | 措辞 |
|---|---|---|
| **已核实游戏环节时长** `verifiedSec` | 满足 §1「已核实」的环节 | 唯一能写「玩了 X 小时」的数字 |
| **关联录像时长** `associatedSec`（包含已核实） | 边界只到分 P 的环节；只挂一款游戏、没有时间轴的整场录像 | 「相关录像约 X 小时」，不能写成游玩时长 |
| **未知** | 多游戏场次没有时间轴；缺时长；录像不全的部分；`kind: unknown` 环节 | 只计场次，不计入任何小时数 |

规则：

- 一场只按基准来源计时，不同来源的时长永远不相加、不取平均；用基准来源自己的分 P 时长，不用条目的 `duration_min`。`duration_min` 只用于没有时间轴的单游戏场次。
- 同一场里各游戏的关联录像时长之和，不超过这场的录像时长（测试守住这条）。
- 系列父 ID（`src/lib/games.ts` 的 `SPECIFIC_GAME_PARENTS`，如 `maplestory` ← `maplestory-classic`）与具体作品同挂时算一款：判断「这场是不是多游戏」时折叠掉父 ID；父 ID 不要求单独有环节，系列页按具体作品的环节计时。
- 录像不全（`coverage` 不是 `complete`）或有 `unknown` 环节时，这一场的数字只是**下限**。
- 「未知」部分可能属于这一场的任何一款游戏，计算模块给出每款游戏的上限 `unknownUpperSec`；有长度不明的部分时 `upperOpen` 为真。

## 4. 界面表达

- 「X 小时」只用在已核实时长上；关联录像时长写「相关录像约 X 小时」，并说明其中包含聊天和按分 P 划分的部分。
- **在多游戏场次大量未拆分之前，不提供任何「游玩时长排行榜」。** 扣掉未知部分后的排序只是「已知录像」的排序，不能用「玩得最久」「游玩时长榜」这类标题。
- 凡是按时长排序或展示时长的位置，都必须同时显示：
  1. **已核实量**（为 0 时写「尚未核实」）；
  2. **覆盖程度**：时长归属已知的场次 / 全部场次；
  3. **未知部分**：未拆分场次数，以及区间上限（「相关录像 86–130 小时 · 3 场未拆分」；上限开放时写「130+」）。
- 两款游戏的区间互相重叠时，不能把先后读成谁玩得更久；界面直接画出区间，不只给名次。
- 只放得下前几名、没空间同时显示这三项的位置（首页预告、统计页「陪伴最久」），按**场次数**排序，时长作为附属信息带区间显示。
- 「游玩时长排行」只在计算模块给出 `playtimeRankable` 时才可出现：时长归属全部已知，没有下限场次和未知上限，且已核实时长 ≥ 关联录像时长的 80%（`PLAYTIME_RANK_MIN_VERIFIED_SHARE`）。前台不自行判断。

## 5. 跳转

逐段入口取各环节起点（`buildJump`）；场次摘要默认取这款游戏第一个环节的起点，同场回切的各段在章节列表分别提供入口：

- B 站：`/video/<BV>/?p=<页号>`；只有精度不是 `part`、且分 P 内时间大于 0 时，才加 `&t=<秒>`。B 站页号越界会退回 P1 而 `t` 照样生效，所以页号只能来自时间轴快照。
- A 站：`/v/ac<号>_<数组序>`，没有可用的秒级参数，只能落到分 P 开头。

快照里的 `id` 和 `duration_sec` 用来定期核对平台是否重排或替换了分 P。
