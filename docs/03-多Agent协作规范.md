# 多 Agent 协作规范与交接文档

> 版本 v0.1 · 配套《01-策划》《02-功能设计》
> 本文是**所有 Agent 的唯一权威协议**。任何 Agent 在动手前必须先读它；与本文冲突的临时指令，以人类维护者的明确指示为准。

## 〇、为什么需要这份文档

这个项目由多个异构 Agent（Claude / Codex / DeepSeek / 未来的其他模型）分工完成。它们**不共享上下文、不共享记忆、不一定能访问同一个仓库**。因此协作只能靠两件东西：

1. **明确的边界** —— 谁能改哪些文件，谁绝对不能碰。
2. **机器可校验的契约** —— 交接物必须能被脚本自动验收，而不是靠人读一遍觉得「差不多」。

一切协作的收敛点是 **`data/**.yaml` 的 Schema**。它既是数据格式，也是 Agent 之间的接口定义（IDL）。

## 一、角色分工

| 角色 | 建议 Agent | 职责 | 可写路径 | 禁止 |
|---|---|---|---|---|
| **A · 架构与前端** | Claude | 站点主体设计、Schema 定义、组件实现、视觉与交互 | `src/**`、`docs/**`、`src/lib/schema.ts` | 不批量手写 `data/**` 业务数据（仅可写少量 fixture） |
| **B · 数据采集** | DeepSeek | 检索公开资源、核实链接、产出结构化条目 | `data/entries/**`、`data/games.yaml`、`data/accounts.yaml` | 不改 `src/**`、不改 Schema、不改构建配置 |
| **C · 工具与自动化** | Codex | 校验脚本、索引构建、存活检查、抓取器、CI | `scripts/**`、`.github/**`、测试 | 不改 UI 组件、不改 Schema 定义 |
| **D · 审校** | 任意（换一个模型做，别自审） | 数据抽检、链接复核、去重、置信度评级 | 只提 review 意见与修订 PR | 不新增未经核实的条目 |
| **人类维护者** | 你 | 定 Schema 变更、合并 PR、裁决争议 | 全部 | — |

**唯一的强约束：Schema（`src/lib/schema.ts` 与 `docs/02-功能设计.md` 的数据模型章节）只能由角色 A 修改，且必须同步更新本文与示例数据。** 其他角色发现 Schema 不够用时，走「Schema 变更请求」流程（见第五节），不得私自加字段。

## 二、交接物的形态

Agent 的能力差异很大：有的能直接读写仓库，有的只能在对话框里吐文本。因此定义两种交接通道：

### 通道 1 · 直接提交（有仓库访问权的 Agent）
- 单独分支：`data/<年份或批次>`、`feat/<功能>`、`chore/<工具>`
- 一个 PR 只做一件事；数据 PR 不夹带代码改动，反之亦然
- PR 必须通过 CI（`npm run validate`）才能合并

### 通道 2 · 文本交付（无仓库访问权的 Agent，如对话式 DeepSeek）
输出**一个完整的、可直接落盘的 YAML 文件内容**，外加一段交付说明。禁止输出「片段」「省略号」「同上」。格式见第四节的任务包模板。人类或角色 C 负责落盘 + 跑校验。

## 三、工作流

```
人类切分任务
   │
   ├─→ [任务包] ──→ 角色 B（DeepSeek）采集
   │                     │ 产出 YAML
   │                     ▼
   │                 npm run validate   ← 角色 C 提供的校验脚本
   │                     │ 通过
   │                     ▼
   │                 角色 D 抽检（≥20% 随机复核链接可达性与日期）
   │                     │
   │                     ▼
   │                 人类 merge
   │
   └─→ [功能卡] ──→ 角色 A 实现前端 ──→ 角色 C 补脚本/CI ──→ merge
```

**铁律：数据入库前必须过校验脚本。** 没有 `npm run validate` 通过的截图/输出，PR 一律不看。

## 四、数据采集任务包（发给 DeepSeek 的标准格式）

每次派活用这个模板，**一次只派一个明确切片**（一个年份、一个平台、一个游戏系列），不要给开放式的「把所有资源都找出来」。

````markdown
# 采集任务 #<编号>

## 范围（只做这个范围，超出的忽略）
- 对象：女流66
- 时间：2018-01-01 ~ 2018-12-31
- 平台：bilibili（仅这一个）
- 类型：live（直播场次及其录播）

## 你要产出的文件
`data/entries/2018-bilibili-live.yaml`，内容为一个 YAML 数组，每项严格符合下方 Schema。

## Schema（不得增删字段；不确定的可选字段直接省略，不要填空字符串）
<粘贴 docs/02-功能设计.md 的 Entry 定义>

## 硬性规则
1. **只收录你实际访问/检索到的公开链接。** 一条都不许编造 BV 号、日期、时长。
2. 拿不准的信息：`confidence: low` + 在 `note` 里写明存疑点。宁可留空，不可猜测。
3. 同一场直播的多个录播源，合并进同一条目的 `sources`，不要拆成多条。
4. `id` 规则：`YYYY-MM-DD-<type>-<两位序号>`，同日多条按时间顺序编号。
5. 游戏名统一用 `data/games.yaml` 里已有的 `id`；确实是新游戏，在交付说明里单列出来，不要自己往 games.yaml 里塞。
6. 日期用直播的**实际开播日**，不是录播的上传日。区分不了就标 `confidence: low`。

## 交付时同时给出
- 覆盖情况：本范围内共找到多少场，估计遗漏多少，哪些月份是空的
- 存疑清单：所有 `confidence: low` 的条目及原因
- 新游戏清单：需要人类添加到 games.yaml 的游戏
- 你**没能**确认的东西（比这更重要：明确说出来，不要用合理猜测填上）
````

### 反模式（明令禁止）
- ❌ 用「大概是2015年左右」这种模糊时间填进 `date`
- ❌ 把搜索结果标题直接当作直播标题而不核实
- ❌ 为了凑数量把切片当成完整录播登记
- ❌ 输出「以下省略 N 条，格式同上」

## 五、Schema 变更请求（RFC）

任何 Agent 发现字段不够用：在 `docs/rfc/` 下新建 `NNN-<短名>.md`，写清楚：现状 → 缺什么 → 影响哪些已有数据 → 迁移方式。角色 A 评估并实现，人类拍板。**在 RFC 合并前，采集方按现有 Schema 继续干活，多余信息暂存 `note` 字段。**

## 六、冲突与去重

- 两个 Agent 提交了同一场直播 → 以 `id`（日期+类型+序号）为唯一键，合并 `sources`，保留 `confidence` 更高的一方的标题与时间。
- 数据 PR 之间的 YAML 冲突：按年份分文件已经把冲突面降到很低；真冲突时以先合并者为准，后者 rebase。
- Agent 之间**不得互相直接改对方的产物**：发现错误提 issue 或提修订 PR，由人类决定。

## 七、每个 Agent 的会话起手式

任何 Agent 接手时，第一步必须做完这三件事再动手：

1. 读 `AGENTS.md`（根目录，机器可读的精简版规则）
2. 读本文对应自己角色的那一行，确认可写路径
3. 声明本次任务的**范围与产出物**，与人类确认后再开工
