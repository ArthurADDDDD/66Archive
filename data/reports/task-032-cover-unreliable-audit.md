# Task 032：多日期合集封面误导审计

> 触发：用户人工核对 `2015-02-04-live-01`《风之旅人》时发现播放页封面是露脸镜头，
> 但女流 2015 年 2 月刚开播不久时并未露脸，与该条目实际内容不符。

## 问题机制

站内条目若没有自己的 `cover` 字段，展示层会调用 B 站 `x/web-interface/view` 接口
按 `bvid` 动态拉取封面（`src/lib/bilibili.ts`）。这个接口**只返回整条投稿视频的封面，
不区分 `?p=` 分 P**。

「过往精彩录像补投」这类账号（女流录像小屋、影忆丶Yi）经常把好几个月、好几个真实
直播日剪进同一条 B 站投稿的不同分 P 里。这种情况下，同一个 BV 号的封面会被**所有
挂在它名下的日期条目**共用，但封面画面实际上只代表其中某一天——如果这些日期横跨
了外观 / 场景明显变化的时间段（例如是否露脸），观众会看到一张来自别的日期的封面。

## 已核实的具体案例

`BV1KW411g7Hr`《风之旅人》补投：P1.1/P1.2 对应 2015-02-04（未露脸期），
P2.1/P2.2 对应 2015-07-22、P3 对应 2015-08-20（均已露脸）。经 bilibili API
核实（`x/player/pagelist`），三个日期在同一条视频内确认无误，但该 BV 的官方封面
图取自后两个日期，用在 2015-02-04 条目上会显示错误的露脸画面。

## 全库扫描结果

按「同一个 B 站 BV 号（忽略 `?p=` 参数）被跨多个不同日期的条目引用，且没有条目/来源
自带 `cover`」筛出以下 8 个 BV，共 77 处来源、覆盖 2015-02 至 2016-07 的条目：

| BV | 涉及日期跨度 | 涉及条目数 | 备注 |
|---|---|---|---|
| `BV1KW411g7Hr` | 2015-02-04 / 07-22 / 08-20 | 3 | 已确认视觉错误（本次触发案例） |
| `BV13W41187BJ` | 2015-02-05 / 02-06 | 2 | 相隔 1 天，视觉风险低 |
| `BV1bW411W74m` | 2015-03-02 / 03-10 / 03-11 | 3 | 相隔数天，视觉风险低 |
| `BV1ef4y1Y7T2` | 2015-07-05 ～ 12-19（19 个日期） | 19 | 影忆丶Yi《心灵砒霜-2015补档》，跨 5 个月，风险与风之旅人同级 |
| `BV1ZN411o7VN` | 2016-01-01 ～ 07-03（13 个日期） | 13 | 影忆丶Yi《心灵砒霜-2016补档》，跨 6 个月，风险与风之旅人同级 |
| `BV1fW411i7Lr` | 2016-03-24 / 03-25 / 03-28 | 3 | 相隔数天，视觉风险低 |

其中 `BV1ef4y1Y7T2` 与 `BV1ZN411o7VN` 两个「心灵砒霜」补档合集横跨的时间最长（5～6
个月），理论上风险与本次触发案例同级，只是尚未逐条人工看片确认是否真的出现可见的
封面错配。

## 已完成的处理

1. **`src/lib/schema.ts`**：`Source` 新增可选字段 `cover_unreliable: boolean`，
   语义为「这个来源没有自己的 cover，且平台按视频整体返回的封面不代表这一条目实际
   内容，展示层不应再用平台接口动态拉取封面兜底」。
2. **数据层**：给上表 8 个 BV 涉及的全部 77 处来源标记 `cover_unreliable: true`
   （`data/entries/2015-douyu-live.yaml`、`data/entries/2016-early-douyu-live.yaml`）。
3. `2015-02-04-live-01` 的 note 补充了用户核实的具体证据（封面取自 P2/P3 而非 P1）。

## 展示层修复（2026-08-31 完成，由 Claude 直接实现）

`cover_unreliable` 字段已经打通到展示层：

- `src/lib/data.ts`：`TimelineSource` 新增 `coverUnreliable`，`toTimelineEntries` 从
  `source.cover_unreliable` 映射过来。
- `src/app/e/[id]/page.tsx`：组装 `WatchSource` 时同样带上 `coverUnreliable`。
- `src/components/EntryRow.tsx`、`src/components/EntryWatch.tsx`：当选中来源的
  `coverUnreliable` 为 true 时，跳过 `getBilibiliVideoMeta` 的动态拉取（不发请求，
  不用返回值兜底），效果等同于「这个来源没有封面」——时间轴行退化为无图状态，
  详情页封面卡片显示已有的「封面待补」占位。

已在本地验证：`2015-02-04-live-01`（本次触发案例）不再发出封面请求、显示
「封面待补」；未标记的普通条目（如 `2016-06-12-live-01`）自动拉取封面的行为不受影响。

## 手动截取分 P 封面（2026-08-31 完成，用户要求跳过「只索引不搬运」的默认限制）

用户明确要求不再显示「封面待补」占位，而是从每个条目对应的正确分 P 里手动截一帧
作为封面——这类封面本质上无法从平台接口精准取到（B 站封面按整条投稿返回，不分 P），
所以这是一次经用户批准的特殊处理，不代表放宽全站的选源原则。

流程：
1. 用 `x/player/pagelist` 拿到每个条目对应分 P 的 `cid` 与 `duration`；
2. 用 `x/player/playurl`（`qn=32`，游客可访问的 360P `durl`）拿到可直接读取的视频直链；
3. `ffmpeg` 按该分 P 时长的 40% 处截一帧（同时避开片头黑屏/加载画面与片尾），
   缩放到宽 960 输出 JPG；
4. 人工抽查多张确认没有黑屏/白屏/加载图之类的坏帧，对唯一一张明显有问题的
   （`2016-04-20-live-01`，命中黑屏）换时间点重截；
5. 存入 `public/images/covers/<entry-id>.jpg`，给对应条目补上
   `cover: "/images/covers/<entry-id>.jpg"`（条目级覆盖，优先级高于来源级的
   `cover_unreliable` 动态兜底，因此这些条目现在不会再触发那条兜底逻辑）。

上表 8 个 BV、55 个不同日期条目已全部截图入库并写回 `cover` 字段（`77` 处标记
`cover_unreliable: true` 的来源里，同一天的多个来源共用一张日期级封面）。

## 后续建议

- 后续若发现某张截图选到了不合适的画面（比如恰好是黑屏、加载图、或者不能代表
  当天内容），直接换时间点重截替换 `public/images/covers/<id>.jpg` 即可，不需要
  改 `cover_unreliable` 标记。
- 未来任何新导入的「过往精彩录像补投」类多日期合集，导入时就应该检查 BV 官方封面
  对应哪个分 P/日期，不匹配就直接标 `cover_unreliable: true` 并考虑同步截图补
  `cover`，不要等用户发现。
