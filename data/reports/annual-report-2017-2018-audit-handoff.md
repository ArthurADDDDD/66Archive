## 4. 建议的改进方向

### 4.1 不要只把这些数字写在 Markdown：建立年度报告结构化层

建议后续新增类似：

```text
data/annual-reports/2017.yaml
data/annual-reports/2018.yaml
```

建议字段：

```yaml
year: 2018
source:
  kind: annual-report
  author: 女流66
  platform: douyu-yuba
  published_at: 2019-01-02
reported:
  live_days: 275
  live_hours: 1126
  category_days:
    game: 196
    xinling_pishuang: 39
    outdoor: 22
    other: 20
  games_count: 112
  longest_day:
    date: 2018-11-29
    minutes: 660
  barrage:
    total: 15477550
    daily_average: 56282
    max_day:
      date: 2018-01-21
      count: 236323
  xinling_pishuang:
    sessions: 39
    emails: 642
    email_categories: {}
```

然后由构建脚本同时产出：

- `reported_*`：年度报告原始值；
- `derived_*`：当前 `data/entries` 实时计算值；
- `delta`：两者差异。

这样以后 Data Agent 补档后，差异会自动缩小，不需要反复人工重做年度审计。

### 4.2 区分三种“真值”，禁止互相覆盖

1. **官方年度报告真值**：适合保存全年直播日、全年时长、弹幕、邮件等平台/内部统计。
2. **录播文件真值**：适合保存现存视频真实时长、分 P、游戏内容。
3. **档案派生真值**：当前仓库能确认到的 unique days / duration / games。

发生冲突时应并列保存，例如：

- `reported_duration_min: 575`
- `archived_duration_min: 568`

而不是为了年度数字好看，直接改 `duration_min`。

### 4.3 系列统计需要“内容数”和“直播场次数”双口径

尤其是心灵砒霜：

- 切片也可以属于“心灵砒霜内容”；
- 但切片不能算“直播了一次”。

建议系列模型补：

- `content_count`
- `live_session_count`
- 可选 `unique_live_days`

页面文案根据语义选对应字段。

### 4.4 年度大事件应成为 Chronicle 的证据层，不要只依赖直播标题

年度报告提供了很多“当天直播标题里看不出来”的历史意义，例如：

- 首位皇帝
- 首次语音直播
- 主机板块第 1 名
- 首次吃鸡
- 200T 鱼丸
- 直播关注 200W

建议 Data Agent 核实后写入：

- entry `note`：当日事实；
- Chronicle：真正值得进入叙事的节点；
- source：年度报告作为来源之一。

不要为了这些事件新建重复 `live` 条目。

### 4.5 年度游戏数要保留“当年报告口径”

年度报告的“82 / 112 款”不一定等于今天仓库的 unique game slug：

- DLC 是否单独算；
- 同系列不同版本是否单独算；
- 一场多游戏如何计数；
- 年报可能有排版漏项。

因此应保留 `reported_games_count`，再另算 `derived_unique_games_count`，并建立人工 mapping，而不是硬凑数量。

### 4.6 邮件分类必须保留年度 taxonomy

2017：情感 / 规划人生 / 人际交往 / 其他。

2018：情感 / 人际交往 / 规划人生 / 学习工作 / 其他。

分类体系本身发生变化，是历史信息的一部分。不要把旧年的“其他”强行重分到新分类。

### 4.7 把年度报告原图纳入长期证据保存

建议后续确定版权/仓库体积策略后，为两套报告建立稳定资产索引：

- 原图文件名
- SHA-256
- 原始发布平台 / 帖子 URL（若能找回）
- 发布时间
- 归档位置

即使不把大图直接提交 Git，也至少应保存 source manifest，防止以后只剩二手转述。

8. 重点检查 2017 的“首次吃鸡”“200T 鱼丸”“关注 200W SOLO 演唱会”等是否已经进入可搜索的事件层。

### P2：把不可再生统计正式结构化

9. 建立年度 report schema，录入直播天数、时长、内容分类天数、弹幕、砒霜邮件、年度游戏数。
10. 保存两年的年度邮件分类 taxonomy。
11. 保存年度游戏推荐、户外地点、弹幕热词为历史 snapshot；这些不要和实时派生排行榜混用。
12. 为年度报告原图建立稳定来源索引 / hash / 原帖 URL。

---

## 6. 核验原则

- 年度报告是**强锚点，不是覆盖命令**。
- 单场录像与年度汇总冲突时，先记录 delta，再找原因。
- 不为了补齐“264 / 275 天”“1069 / 1126 小时”而制造无来源条目或修改时长。
- “有录像”不等于“历史意义已经记录”；事件语义应单独补。
- “系列内容条目”不等于“直播场次”。
- 新的补档或修正完成后，应重新自动计算 `derived` 并与 `reported` 对比。

这两套年度报告最重要的价值不是证明某一条录像存在，而是提供了**平台时代已经难以重新获得的年度总量、弹幕、邮件、事件和栏目口径**。后续应把它们作为 2017–2018 的一级年度校验源长期保留。
