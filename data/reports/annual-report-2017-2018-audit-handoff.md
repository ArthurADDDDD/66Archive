# 2017–2018 女流66年度直播报告：数据锚点与 Data Agent 交接

> 整理日期：2026-08-29
>
> 用途：保存两套鱼吧年度直播报告中**很难从现存录播重新恢复的年度级数据**，并把报告明确事实、当前档案核对结果、冲突和调查假设严格分开，供 Data Agent 后续逐项处理。
>
> 证据来源：用户保存的 2017、2018 年度报告原图。两套图均带 `@女流66 / yuba.douyu.com` 水印；目前应描述为**主播鱼吧年度总结 / 高价值一手或近一手统计资料**。在找回原鱼吧帖子、制作说明或数据出处以前，不把其中每个数字表述成“斗鱼后台官方统计”。
>
> 核心原则：**年度报告是强校验源，不是覆盖命令。**尤其是直播时长，年报与现存录播使用的统计口径可能天然不同：录播员通常会保留开播前聊天、等待、转场等完整过程，而年度总结可能按正式内容开始、平台开播状态或其他内部口径计算。因此分钟级时长差异默认只作参考，不作为修改逐场 `duration_min` 的硬条件。

## 0. 状态约定

后续 Data Agent 处理本文时，建议给每个发现明确标记状态，避免把推论写成事实：

| 状态 | 含义 |
|---|---|
| `reported` | 年报图片明确写出的原始信息 |
| `confirmed` | 已与当前档案、录像或第二来源交叉确认 |
| `conflict` | 年报与当前档案存在需要解释的明显差异；不等于当前档案一定错 |
| `hypothesis` | 根据上下文产生的调查假设，禁止直接据此建条目或改日期 |
| `resolved` | 已找到足够证据解释并完成修正 / 记录 |

时长差异默认属于**参考性差异**，只有发现录像本身明显缺段、条目录入错误或第二来源能证明问题时，才升级为需要修改数据的 `conflict`。

## 4. 后续改进方向

### 4.1 先保留“年度报告结构化层”的方案，页面暂缓

未来可以考虑新增：

```text
data/annual-reports/2017.yaml
data/annual-reports/2018.yaml
```

用于保存年报原始统计、来源、事件、邮件 taxonomy、年度推荐等。

**但暂不推进独立“年报页面”。**页面属于未来展示层想法，当前只保留 TODO，避免为了新页面提前扩展前端和数据模型。

如果以后实施结构化层，建议最少分开：

- `reported`：年报原始值；
- `archived`：当前档案 / 录像保存值；
- `derived`：构建时从 `data/entries` 实时计算的值。

其中时长只做并列参考，不把 `reported_hours` 当作必须逼近的验收目标。

### 4.2 区分“年度报告事实”和“当前档案事实”

例如：

```yaml
year: 2018
reported:
  live_days: 275
  live_hours: 1126
  games_count: 112
  category_day_counts:
    game: 196
    xinling_pishuang: 39
    outdoor: 22
    other: 20

audit:
  category_sum: 277
  category_sum_vs_live_days: 2
  category_overlap_status: unresolved
```

这样能够保存年报原貌，又不会强迫今天的数据去“凑”年报数字。

### 4.3 直播日数量比直播时长更适合作为补档锚点

- `unique live days` 可以帮助发现完全缺失的直播日；
- 分钟级时长容易受录播范围、开播前等待、正式内容起点、平台计时规则等影响；
- 因此补档优先看“有没有这一天”，而不是先追求全年小时数完全一致。

### 4.4 系列统计需要双口径

尤其心灵砒霜：

- `content_count`：栏目相关的所有内容，包括合理保留的切片；
- `live_session_count`：真正的直播场次；
- 可选 `unique_live_days`。

页面文案按语义选择对应字段，避免“已收录 X 条相关内容”被误写成“直播了 X 期”。

### 4.5 年度大事件应成为 Chronicle / note 的证据来源

年度报告最能补强的并不是已有录像本身，而是直播标题之外的历史意义，例如：

- 首位皇帝
- 首次语音直播
- 主机板块第 1 名
- 首次吃鸡
- 200T 鱼丸
- 关注 200W

Data Agent 核实后优先：

- 给已有 entry 补 `note`；
- 真正重要的节点再进入 Chronicle；
- 年报作为 source 之一。

不要为了事件新建重复 `live` 条目。

### 4.6 年度游戏数保留年报口径，不硬凑当前 game slug

“82 / 112 款”不一定等于今天仓库 unique game slug，因为可能存在：

- DLC 是否单独计数；
- 同系列不同版本；
- 一场多游戏；
- 年报排版漏项。

因此未来应保存 `reported_games_count` 与 `derived_unique_games_count` 两套值，需要时再人工 mapping。

### 4.7 邮件分类必须保留当年的 taxonomy

2017：情感 / 规划人生 / 人际交往 / 其他。

## 6. 核验原则

- 年度报告是**强锚点，不是覆盖命令**。
- `reported`、`confirmed`、`conflict`、`hypothesis` 必须分开。
- 不把主播鱼吧年度总结未经证明地称为“斗鱼后台官方统计”。
- **时长不是硬条件。**录播全程与年度统计正式开始口径不同属于合理可能。
- 直播日数量可以帮助寻找缺档，但也不能为了补齐 264 / 275 天制造无来源条目。
- “有录像”不等于“历史意义已经记录”；事件语义应单独补。
- “系列内容条目”不等于“直播场次”。
- 新补档完成后可以重新生成 `derived` 与 `reported` 的差异，但差异本身不是错误证明。

这两套年度报告最重要的价值，是保留了**平台时代已经很难重新获得的年度总量、弹幕、邮件、年度事件、游戏盘点和栏目口径**。它们应该长期作为 2017–2018 的高价值年度校验源，但不要求今天的录播档案在每一个统计口径上与之完全一致。
